# OpenUI documentation

## When to use this skill

- Writing or editing a docs page.
- Adding a page, framework guide, or navigation entry.
- Changing `llms.txt`, `llms-full.txt`, `llms/**`, or `schema.json`.
- Fixing a docs build or `llms:validate` failure.

## Canonical sources

| Artifact                         | Canonical source                          | Generated by              |
| -------------------------------- | ----------------------------------------- | ------------------------- |
| Site pages and LLM docs          | `apps/docs/content/docs/**/*.md`          | —                         |
| `apps/docs/public/llms.txt`      | all canonical pages                       | `bun run llms:generate`   |
| `apps/docs/public/llms-full.txt` | all canonical pages                       | `bun run llms:generate`   |
| `apps/docs/public/llms/**/*.md`  | one page each                             | `bun run llms:generate`   |
| `apps/docs/public/schema.json`   | `packages/core/src/config/schema.ts`      | `bun run schema:generate` |
| `apps/docs/public/registry/`     | `registry/`                               | `bun run registry:public` |
| Registry index and items         | `registry/openui-registry.json` + sources | `openui build`            |

Never edit anything in the right-hand "Generated by" column. Change the source
and regenerate.

## Page format

Every page starts with YAML frontmatter containing scalar values:

```markdown
---
title: Configuration
description: How openui.json is discovered, validated, and resolved.
order: 2
group: reference
---

# Configuration

…
```

- `title` is used in the site and in the LLM index.
- `description` becomes the one-line LLM index entry; write it as a complete
  sentence.
- `order` sorts pages within a group.
- `group` places the page in the sidebar: `reference` (default), `components`,
  or `frameworks`. Framework pages must also live under `frameworks/` so
  ordering and links stay consistent.
- `component` (components group only) names a registry component. The site then
  renders a framework-tabbed **Source** section from `registry/r/*.json`, so the
  snippet is byte-identical to what the CLI installs. Never hand-copy component
  source into a page.
- `demo` (components group only) names a live preview registered in
  `apps/docs/src/components/Demo.astro`. Add new previews as
  `apps/docs/src/components/demos/<Name>.astro`, then add the entry to `DEMOS`.
- Do not use nested YAML; the parser reads `key: scalar` only.
- Start the body with a single H1 that matches `title`. The generator emits its
  own title header and strips the body H1, so the generated file has exactly one
  H1 and one `Source:` line.

Component pages live in `apps/docs/content/docs/components/`. The landing page
is `components/index.md`, served at `/docs/components`; every other file is
served at `/docs/components/<name>` because the route strips an `/index`
suffix.

## Writing style

- Lead with the command or decision, not background.
- Use fenced `bash` blocks for commands, with one command per line.
- Link between pages with site-absolute paths: `[CLI](/docs/cli)`. The
  generator rewrites these to `https://openuii.vercel.app/docs/...` for raw LLM files.
- Do not link to a page that does not exist; validation fails.
- Prefer tables for option/flag references.
- State beta limitations explicitly instead of implying production readiness.

## Required pages

`REQUIRED_SLUGS` in `scripts/lib/docs.ts` lists pages that must always exist:
getting-started, configuration, cli, `components/index`, every
`components/<name>` page, registry, theming, contributing, and the four
framework guides. `validateLlms` fails if one is missing, and
`apps/docs/test/llms.test.ts` asserts the list.

When adding a page:

1. Create `apps/docs/content/docs/<slug>.md` (or `frameworks/<name>.md`).
2. Add frontmatter and body.
3. If it must always exist, add the slug to `REQUIRED_SLUGS`.
4. If it introduces links from other pages, fix those links.
5. Run `bun run llms:generate` and `bun run llms:validate`.
6. Run `bun run build:docs` to confirm the route builds.
7. Commit the canonical page **and** the regenerated `public/llms*` files.

The site route is generated automatically: `apps/docs/src/pages/docs/[...slug].astro`
renders any page found by the content collection, so no route file is needed.

## Generation pipeline

`bun run llms:generate`:

1. Walks `apps/docs/content/docs` recursively, sorted for determinism.
2. Parses frontmatter and body.
3. Writes one `llms/<slug>.md` per page with a "do not edit" header and source
   URL.
4. Writes `llms.txt` with root pages, framework pages, and machine-readable
   links.
5. Writes `llms-full.txt` with every page joined by horizontal rules.
6. Deletes and recreates `public/llms/` so removed pages cannot linger.

`bun run llms:validate` rebuilds the expected output in memory and fails on:

- a missing required canonical page;
- a missing or stale generated file;
- an empty generated file;
- a link to an unknown docs page, a missing public file, or a broken relative
  `.md` link;
- a private key marker in generated output.

Two-pass note: validation compares generated output to committed files, so run
`llms:generate` after any content edit.

## JSON Schema

The schema is generated from the core TypeScript definitions:

```bash
bun run schema:generate
```

Change `packages/core/src/config/schema.ts` first. The docs page for
configuration should match the schema fields and defaults; if you add a field,
update both.

## Docs site

- Astro 7 + Tailwind CSS v4.
- Content collection config: `apps/docs/src/content.config.ts`.
- Pages: home, docs index, and `docs/[...slug]`.
- Styling: `apps/docs/src/styles/global.css`.
- Build: `bun run build:docs`, which first copies the registry to
  `apps/docs/public/registry/` and then runs `astro build`.
- Dev server: `bun run dev` (or `bun run --cwd apps/docs dev`).

`apps/docs/public/registry/` is generated and gitignored. Do not commit it or
edit it; it is recreated on every build.

## Public URLs to verify

After a deploy, these must resolve:

- `/`
- `/docs/getting-started`
- `/docs/configuration`
- `/docs/cli`
- `/docs/components`
- `/docs/components/{button,input,textarea,select,checkbox,radio,label,field,theme}`
- `/docs/registry`
- `/docs/theming`
- `/docs/contributing`
- `/docs/frameworks/{react,svelte,astro,vue}`
- `/llms.txt`
- `/llms-full.txt`
- `/llms/{slug}.md`
- `/schema.json`
- `/registry/index.json`

## Pitfalls

- Editing `apps/docs/public/llms*` is overwritten and fails validation.
- A page without `description` produces a thin LLM index entry.
- Using nested YAML frontmatter silently yields wrong values; keep it scalar.
- A link to `/docs/foo` with no `foo.md` fails `llms:validate` and `verify`.
- `apps/docs/public/registry/` is not committed, so a fresh clone must build
  before serving registry URLs locally.
- The docs build runs the registry copy script; replacing the build command
  without it breaks registry URLs.
